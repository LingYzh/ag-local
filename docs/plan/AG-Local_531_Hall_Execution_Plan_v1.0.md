### 1.2 TS 状态缺陷的具体依据

`service-supervisor.ts` 的 `waitForExit()` 在退出等待超时时调用 `failRecord()`，设置 `FAILED / WORKER_EXIT_TIMEOUT`。随后 `handleExit()` 仅根据 `expectedExit`、`shutdownAcknowledged` 和退出码判断是否正常，没有保存并优先使用该实例此前的故障。已收到关闭确认的子进程迟到退出且退出码为 0 时，会进入 `STOPPED` 分支并清空 `lastError`。[S1]

本轮用实际 TS 模块构建输出、注入的 EventEmitter 模拟子进程及 100 ms 等待上限完成复现，没有启动 Electron 或真实工作进程：

| 观察点 | 状态 | 错误 |
| --- | --- | --- |
| READY 后请求关闭，子进程确认但不退出 | 等待退出 | 尚未超时 |
| 退出等待超时，`stop()` 拒绝 | FAILED | WORKER_EXIT_TIMEOUT |
| 同一实例随后发出 `exit(0)` | STOPPED | null |

被测监督器源文件 SHA-256 为 `a797b3762cf33538de21c25d89cc85056dec468baf67c08ca66c40e909b7348a`。本机复现脚本和包含依赖源码哈希的结果位于 `desktop/qa/review-7aea8f0/`；该目录被忽略，本文不把它计为已交付的公共回归测试。正式修复必须把对应测试加入已跟踪的 `desktop/tests/lifecycle.test.ts`。

Python 监督器已有实例级 `failed`、`lastFault`，退出处理会保留之前的故障；其测试也覆盖迟到退出。现有进度文档中的“关闭超时后迟到退出不得抹掉故障”目前只能指这组 Python 测试，不能据此认为 TS 路径也已覆盖。[S2]

### H01 修复监督器故障保持

修改范围限于 `desktop/src/main/service-supervisor.ts`、`desktop/tests/lifecycle.test.ts` 及相关验证记录。采用实例级故障记录：发生关闭超时或控制协议故障后，迟到退出只能释放已确认结束的实例所有权，不能自动清除该实例的故障。

退出事实与失败原因分别记录。后续显式启动新实例时才初始化新的无故障状态；旧实例的迟到事件不能污染新实例。重复关闭也不能把既有失败包装成一次成功停机。无需引入按 PID、进程名或端口杀进程的补救路径。

正式回归至少覆盖：

1. 正常确认关闭并及时 `exit(0)`，得到 STOPPED。
2. 确认关闭但不退出，`stop()` 报 WORKER_EXIT_TIMEOUT，状态为 FAILED，所有权仍保留。
3. 超时期间再次启动被拒绝；随后迟到 `exit(0)` 释放所有权，但 FAILED 和原错误保留。
4. 迟到非零退出和重复退出不覆盖最初故障；没有合法关闭确认的退出不能按正常关闭处理。
5. 旧实例结束后显式启动新实例，使用新 UUID；旧回调不能清掉新实例故障或结束其所有权。

完成标准是新增测试先在基线暴露缺陷，修复后通过，并保留现有生命周期、安全和 Python 监督器测试。该修复仅证明状态管理正确，不计作大厅进度。

### H02 固定 Python 工具环境

按用途拆分依赖，而不是复制旧安装的全部 `pip freeze`：控制入口和 framing 当前仅需标准库；静态恢复需要 UnityPy 的公共字符串表及 LZ4 分支所用的 `lz4.block`；证据工具按实际 imports 确认依赖。测试使用 `unittest`，没有必要为现有测试专门引入 pytest。

已知成功环境是 Windows 上的 CPython 3.14.6、UnityPy 1.25.2、lz4 4.4.5。这些版本先作为复现候选，不能直接宣称所有平台均受支持。先核对独立运行时发行来源、安装或压缩包哈希、CPU 架构与所需 wheel 的可得性，再锁定 Windows 验证组合；其他平台另列支持情况。

建议交付位置为 `tools/python/` 下的环境说明、安装脚本、直接依赖输入与带传递依赖和分发文件哈希的锁文件。文件名可在实施时按工具确定，锁文件必须具备以下信息：

- Python 精确版本、实现、架构、发行来源与校验依据。
- 直接和传递依赖的版本、分发文件哈希及平台适用范围。
- 建立新虚拟环境的方法；与旧安装、用户 site-packages、PYTHONPATH 和全局包的隔离方式。
- 如需离线复现，所需 wheelhouse 的生成与校验步骤；wheelhouse 作为显式输入，不提交整个环境目录。

验收分两层：干净 checkout 加独立运行时，应能安装锁定依赖并运行合成测试；真实 schema 再生成还需要用户本地、哈希匹配的 scripts 输入。后者不属于公开仓库自带输入，不能将其缺席伪装成一次成功提取。

真实提取应在固定环境连续生成两份结果并比较。若代码和依赖组合保持原样，核对既有 schema 哈希；若工具源码、报告字段或依赖发生已说明的变化，报告哈希可能合理变化，须区分结构差异、来源元数据变化和不期望的协议变化。不能为追求旧报告哈希而删除新的来源信息。

### H03 补齐可复核验证链

H03A 负责迁入工具、合成测试和补齐当次实验的证据绑定；H03B 负责最小 CI，单独验收，不作为 H06 离线实现或阶段试跑的前置。建议将当前 matcher / analyzer 整理到 `tools/evidence/`，测试放入 `tests/evidence/`。维护范围包括有界读取、PCAPNG / TCP 重组、去重、分帧、显式压缩标志、schema 匹配和脱敏报告；保持离线分析入口，不与游戏业务模块互相导入。

去掉默认指向个人路径的输入与输出。CLI 接受明确输入、schema、预期哈希和新输出目录；输出不得覆盖旧结果。`.gitignore` 继续忽略原始 PCAP、密钥、存档和运行产物，不能简单取消整个 `qa/` 忽略规则来解决源码缺失。

保留并迁入现有 15 项 matcher 测试。按工具职责增加必要的独立合成输入：分片与重传、冲突重叠、长度截断、未知字段、required 缺失、packed / unpacked、singular message 合并、深度和字段数量上限、UTF-8 错误、压缩炸弹及尾随压缩数据等。合成数据优先从零构造，不从官方包中替换几个账号字段后就认定可公开。

真实 238 帧复跑继续使用本地原始抓包。公开报告只记录白名单元数据；固定输入下核对帧数、匹配计数、拒绝原因和剩余字节。报告须增加以下绑定：

| 记录组 | 必需信息 |
| --- | --- |
| 代码 | 源码提交或树身份、工作区是否有改动、实际执行源码文件的 SHA-256 集合 |
| 环境 | OS / 架构、运行时版本及分发标识、依赖锁 SHA、关键依赖版本 |
| 输入 | PCAP SHA、schema SHA、合成夹具 SHA；不嵌入载荷或凭据 |
| 方法 | 工具版本、明确的限额、去重方式、压缩选择规则和脱敏字段表 |
| 结果 | 各方向帧数、匹配 / 未知 / 不完整数量、测试名称和结果、未执行项与原因 |

不要要求报告包含最终承载它自身的提交哈希，这会造成自引用。报告绑定被测源码清单和生成时的基线；结果作为后续提交的证据即可。

对桌面 source / package smoke 重新运行当前检查。报告保留检查名称，不能只保存总数；source 报告绑定实际构建源码，package 报告同时绑定 ASAR 和打包来源。历史 16 项报告保留日期与旧范围，新 19 项结果以新记录替代“当前证据”引用；如果源码后续增加检查，使用真实检查数，不以 19 为固定目标。

最小 CI 先覆盖 `npm ci`、类型检查、Vitest、独立 Python 环境和合成协议测试。Electron smoke 在具备相应桌面运行条件的任务或本地可复核运行中验证；真实客户端与私人 PCAP 不进入公共 CI。只有拿到实际成功运行记录才写“CI 通过”。不为此建设复杂发布流水线。

### H04 保全客户端副本与测试存档

先确认源目录处于可取得一致快照的状态，再生成包含路径、大小、SHA-256、缺失项和遍历错误的完整清单。现有 70,800 文件、约 61.0 GB 的盘点和六项关键哈希是准备材料，不能代替全目录副本核验。原目录中的用户状态、外部配置或缓存路径也需要定位，不能仅靠目录名推断“没有账号数据”。

### H05 恢复最小 SDK 与启动入口

用户已说明没有 TLS keylog，已有 PCAP 不能恢复 SDK HTTPS 正文。继续按已定路线先利用当前客户端与 SDK 的静态材料、合法可读日志和已掌握协议定位，不重复要求同一份不存在的密钥。

按成本从低到高推进：定位直接启动和 SDK 调用点；核对当前版本的端点、方法、请求字段、响应字段及成功 / 失败判断；追踪 SDK 身份如何进入 10038 与 10042；必要时再设计针对缺失字段的补充采样。旧服务器路由只作为搜索线索，不能作为当前契约证明。

输出一份最小 SDK / 入口表，逐项注明版本证据、客户端调用位置、成功条件、失败条件、响应来源和下一阶段触发条件。能经已验证的直接启动路径完成本地登录时，不把启动器更新、公告或其他全量接口列为前置工程。

本地身份与会话令牌由隔离服务生成，只在实验环境中使用。不得把官方抓包里的令牌硬编码为本地登录凭据，也不能用 HTTP 200 加空 `data` 遮盖未知契约。

如客户端要求固定 HTTPS 名称，先给出具体路由、证书名称与 SAN、信任范围、归属标记和撤销步骤。需要修改 hosts、系统信任或其他用户环境且现有授权未覆盖时，在方案具体可审阅后再一次性确认。本文不以计划文件本身授予系统修改权限；不采用全局关闭 TLS 校验作为实现路径。

### H06 接通网关和游戏认证

当前 framing 只覆盖头部和原始 body。开始业务前，需要一个消费当前 IR 的 Python codec / 适配层，并明确压缩、序号及会话规则。不要重新导入旧 `main.py`、全局修改 schema 的旧 codec，或默认成功的旧 middleware。[S6]

先实现当前链所需消息：10038 / 10039、10042 / 10043、10200 及已证明必需的响应；后续消息随实际失败加入。编码与解码必须区分缺省、显式零、合法空消息和未知定义；保持完整命名空间、64 位整数、嵌套、重复字段和已确认的未知字段策略。正文允许合法字段顺序差异，结构和语义按契约比较；帧头仍要求精确一致。

上行 marker 7 / 8、两个方向的 index / server-index 目前只有结构证据。实施中必须从客户端调用或受控试验确认其关联、重置和递增规则，不能先假设它们都是“原样回显请求号”。下行按 compress 标志选择 body，压缩 0 不猜 zlib，压缩 1 解压失败不回落原始 body；解压预算和尾随字节规则写入测试。

会话状态至少区分：连接建立、网关身份已接受、游戏认证已接受、初始化中、大厅阶段、关闭。每个状态允许的消息、状态转移、超时、失败后是否仍可使用同一会话都需要明确。客户端连接之间的账号关联以及退出重登后的会话重建，不靠抓包中的历史值维持。

阶段完成证据应包含实际 10038 后客户端接受 10039 并继续下一阶段，以及实际 10042 后客户端接受 10043 并发出预期后续请求。仅有服务端“已发送”日志、编码成功或 socket 已监听不算通过。

### H07 建立最小大厅 LoginPlan

将当前 219 个游戏下行观测按触发原因逐项归入初始化候选、请求响应、轮询 / 心跳或未确定项；同一命令的不同出现位置可以归属不同类别。跨方向采样时间不直接作为因果证明。先处理阻止当前客户端继续的最早缺口，不要求一次解释全部活动与功能消息。

版本化 LoginPlan 的每个可执行项至少包含：完整消息名、命令号、触发阶段 / 请求、前置条件、顺序或依赖依据、字段数据提供者、必要性证据、失败处理、测试夹具和已验证范围。未确定项可以保留在研究目录中，但不能进入自动发送列表。

响应按当前内容配置与独立测试账号实时生成。时间、账号 ID、会话 ID、服务器序号和其他动态字段由明确提供者产生；将时间和随机源设计为可替换的测试依赖。正式实现不能用官方抓包整帧、历史 `seq <= 192` 或旧 login_push 数据库行直接定义当前初始化。

最小种子只提供进入大厅确实需要的账号 / 内容状态。若客户端需要一个初始角色，先确认当前配置里的合法角色和关联数据；若某个列表允许为空，需要客户端契约或真实试验支持，不能由“protobuf 能编码”推导为业务有效。schema 中的 required 与“大厅业务必需”是不同层次。

必要持久化使用独立测试存档和最小事务边界。保证同一个测试账号在退出重登和服务重启后身份、必要角色及基础设置一致；不提前建设完整历史数据库迁移，也不授予无限资源或全角色来绕过未研究字段。

### H08 完成重登验收及必要壳接入

先通过明确的本地运行命令取得稳定链路，再把已有 Python 监督器接到实际业务入口。SDK、网关和游戏处理尽量由一个受控服务实例拥有；多个实例确有必要时，明确谁管理、谁退出，避免隐式启动辅助服务。

当前 Python 监督器在启动时核对解释器哈希，但业务入口仅解析为真实路径后运行，尚未校验实际入口及其依赖模块、环境与运行制品声明的一致性（`desktop/src/main/python-supervisor.ts`，基线第 103—123 行）。现有控制入口对已声明制品与控制协议的检查不能替代这项校验，也不能因同名角色文件齐全就假定 LoginPlan 或种子语义有效。

实际业务入口接入时，必须把运行制品绑定做成启动准入检查。此要求同时适用于本地命令和桌面监督器，从首次 SDK 或网关等业务监听开始执行：

1. 使用明确、版本化的阶段契约，声明本次启用的阶段、处理器、监听能力及必需制品角色；后续阶段保持禁用。仅校验本阶段实际使用的 schema、内容、LoginPlan、种子等数据，但不得漏掉本阶段必需的依赖。
2. 在导入实际业务模块和开放业务监听前，由受信任的启动校验路径核对实际入口的规范路径与内容哈希、本阶段依赖模块及安装依赖的来源和完整性，以及解释器、依赖锁与实际环境的一致性。仅核对锁文件本身的哈希不足以证明实际安装内容一致；仅解析入口真实路径也不足以证明入口版本正确。
3. 明确工作目录、模块搜索路径和允许的环境配置，拒绝未声明的模块来源或环境偏差，避免校验一份制品却从其他目录导入另一份。校验通过后使用同一组已核验制品启动；不能在校验与使用之间重新选择未经核验的入口或依赖。
4. 必需制品缺失、入口或模块哈希不符、环境不匹配时，启动失败并给出可定位的错误，不开放业务监听、不宣告业务能力就绪。将入口被替换、依赖模块被修改、模块搜索路径或环境偏离声明纳入负向验收，并验证正常组合只开放声明阶段的能力。

启动记录应保存阶段契约、manifest 标识、实际入口及模块校验结果和环境核验摘要，供运行报告引用。事后写入哈希不能替代启动时的阻断检查。新增业务状态需要同步修改控制协议校验器与测试，不能让诊断 worker 冒充业务 worker。

服务 readiness 表示已声明处理能力可用；`hall_passed` 只能来自完整运行验收。现有 UI 只需显示服务实例、目标组合、当前阶段和可定位的错误，避免为了展示进度增加新的通用控制台功能。

## 4 输入保全与 76 个资源的处理原则

G0 的含义沿用原计划：锁定并保全当前候选输入，使静态分析可重复。它不等于大厅兼容，也不等于确认所有索引资源均已存在。[S7]

完整输入清单必须如实包含缺失项。副本文件与原目录对应关系、客户端来源、关键身份轴以及可重复静态分析材料核验完成后，才评估 G0；对缺失资源的阶段必要性另行登记。禁止用“已生成清单”替代这些核验。

进入某个实验阶段时，该阶段已知必需的资源必须完整；当前仍未确定且未触发的缺失项可以继续保留未知，但要有受控观察和停止规则。到达需要它的阶段、出现资源加载错误或无法解释的卡顿时，先定位并处理该资源，不能绕开错误继续宣布通过。

这使受控入口试验不必等待全量资源研究，同时也不把 76 项缺失直接认定为可忽略。G1 报告必须列出仍缺失的资源、在约定大厅流程中的观察结果及能力限制；未触达且仍无法判定的项目可保留未知，不要求证明它们在所有玩法、语言和时间点都可选。实际大厅流程出现未解决的资源依赖或加载异常时不能通过；一次大厅成功也不能据此声明完整资源闭包。

## 5 受控试跑的准入条件

下面是一次阶段试验的准入条件，不是新增的发布或兼容等级：

1. 使用可核对来源与清单的客户端副本；运行参数、资源和数据路径已确认指向实验目录，原始客户端和官方账号状态不参与试写。
2. 当前阶段所需的运行时、实际入口、依赖模块、环境、schema、配置和资源已按 H08 在启动时核验，通过后才开放声明的业务监听；后续阶段明确禁用，不能被兜底成功覆盖。
3. 本地服务实例归属可验证，退出路径已测；H01 关闭状态缺陷已修复。日志包含运行组合、实例和阶段关联信息。
4. 网络路由、监听范围与身份链可解释。尚缺证据的 SDK 请求停在该边界；未经明确隔离，不让测试身份或错误配置流向官方服务。
5. 当前阶段实际执行的工具、处理器及数据有实际语义与哈希绑定；仅在本阶段使用时要求对应 LoginPlan 和测试种子，不要求提前补齐后续阶段制品。阶段契约必须列明必需角色、启用能力和禁用阶段；若现有预检要求全部制品角色，应先显式增加并验证阶段化契约，不得拿合成控制面 fixture 或任意占位 JSON 填满现有十类制品角色，借此开放真实业务端口。
6. 当次目标、预期客户端行为、观察方式和停止条件已记录。失败不会修改原目录、正式档或自动更换版本资源。

允许一次实验只完成 SDK、网关或认证中的一个阶段。下一阶段尚未知时记录最后一个已被客户端接受的响应和首个阻塞点，作为下一次补丁输入。

未知字段不要求无限等待。可以在有当前版本静态依据和有限假设时进行单一受控试验；假设及预期结果必须先登记，失败能明确定位，结果不得提前提升为已确认契约。无法确定合法成功响应时，试验应观察失败或继续补证，不能凭猜测伪造成功。

每次只变更可定位的一组处理逻辑或数据，并保留上次实验配置。出现错误先记录层次：入口、TLS / 路由、SDK、分帧、codec、会话、初始化、内容或存档；修复最早确定的阻塞后复跑相同用例。避免同时改协议、种子与资源，导致成功或失败无法归因。

## 7 数据和报告的最低规格

每次实验使用新的 run ID。运行清单引用以下内容；当前阶段适用项的路径可脱敏，但不能省略版本和哈希。后续阶段未使用的工具、LoginPlan、种子等标记为“不适用 / 阶段禁用”，无需制作占位制品；未执行的大厅、重登等验收也必须如实标记：

- 被测源码提交、未提交变更的来源摘要及关键文件 SHA。
- Python / Node / Electron 实际使用版本、架构与依赖锁。
- 启动时的阶段契约与 manifest 标识、实际入口及依赖模块的完整性校验结果、环境核验摘要，以及通过校验后开放的监听能力；不记录明文密钥或敏感环境变量值。
- 客户端副本来源清单、当前 tuple、SDK、资源索引、scripts、schema。
- 服务配置、LoginPlan、内容快照和测试种子的版本或 SHA；不保存明文密钥。
- 阶段事件、方向内消息顺序、关联 ID、明确错误和退出状态。
- 用户操作、大厅观察或截图、重登结果、重启结果和受保护文件核验。

报告的状态使用“通过”“失败”“未执行”“证据不足”，未执行项不能计入通过。公开仓库保存验证工具、合成夹具和白名单摘要；原始流量、客户端日志中未经审查的正文、账号数据、密钥和测试数据库留在实验目录。

工具报告绑定源码哈希，业务验收还必须绑定实际运行制品及其启动校验记录；报告中的哈希是启动检查的证据，不能充当事后补写的替代检查。一个提交上的离线 matcher 通过、另一个版本服务上的大厅截图，不能拼接为同一组合的 G1。
