## 1 先做什么

**先保全用户已恢复正常的 5.3.1 客户端，核实当前文件组合，从当前实际资源恢复匹配协议，再让它通过本地服务端进入主大厅。通过这一门槛后，逐项接通角色、编队、战斗、结算和邮件，并在接通功能时逐步重构。**

推荐采用增量迁移：短期保留现有 Python 网络与协议实现、WinUI 3 管理外壳，先补版本准入、依赖校验和最小大厅链路；随后在清晰接口后替换业务和持久化。不要把重写所有代码、更换语言或建设完整兼容平台放在首次大厅验收之前。

本方案区分两项状态：

- **当前客户端状态，用户确认**：2026-10-11 15:27，正常客户端已恢复到用户所称最新的 5.3.1。此处没有独立核验官方最新状态、EXE 哈希、SDK 或当前 app/resource 编号
- **本地服务端状态，尚未验证**：当前 5.3.1 经本地服务端进入主大厅仍是第一实施目标。旧 app 307 / resource 229 曾在补入恢复 schema 后进入大厅，只能作历史回归证据

原需求中的 resource 321 是此前观察到的候选，不能直接填写成恢复后 5.3.1 的实际资源版本。旧协议包的哈希和验证结果也不能证明当前 5.3.1 兼容。[E1]

实施时若官方版本已更新，先保存当前 5.3.1 快照，再把更晚版本登记为独立候选并明确本轮目标。保持“最新”的核实时间和来源，不将不同版本文件拼成一个客户端，也不凭更新时间自动替换验收目标。

### 2.2 技术选型结论

**长期主推荐：Vue 3 + TypeScript 管理界面，Electron 薄桌面壳，TypeScript 本地服务，SQLite 存档。当前 5.3.1 阶段继续使用 Python + WinUI 3，Python 同时保留为资源/协议静态恢复工具和差分校验基准。** 这是本方案的建议选型，尚未实施，也不是把用户对技术方案的请求解释成已经批准换栈。

推荐的依据是用户已有 Vue 3 能力、对 TypeScript 的兴趣，以及本地单人项目需要控制维护面。Vue/TS 可以覆盖界面和应用服务，Electron 提供成熟桌面承载；其安装体积、内存和原生模块打包成本是必须实测的代价。团队的 Java/PHP 背景也有价值，但仅为本地服务引入另一套 JVM/PHP 运行时，会扩大部署和调试范围。

| 层 | 长期推荐 | 第一阶段做法与选择理由 |
|---|---|---|
| 管理 UI | Vue 3 + TypeScript + Vite | 先保留 WinUI 3；UI 不直接操作数据库、证书或版本文件 |
| 桌面生命周期 | Electron，主进程只管窗口、服务生命周期与窄 IPC | 不先换壳；迁移后只装载随包发布的本地 UI，禁止任意远程页面获得系统权限 |
| 本地应用服务 | TypeScript，轻量模块化服务；现有 SDK/HTTPS 兼容端点用 Fastify | 初期仍用 Python；首期不引入 Nest，模块和依赖注入收益尚不足以抵消额外维护面 |
| 网关传输 | Node `net`/`tls` + 独立有界分帧器 | 精确保留实测 wire 约定；自定义帧协议不强行套 HTTP 框架 |
| 协议编解码 | Schema IR + 版本适配器；以 protobuf.js 动态描述能力做替换验证 | Python codec 保留到所需帧字节/协议语义等价与真实大厅通过，不直接把旧 JSON 喂给新库就宣称完成 |
| 运行时输入校验 | Zod 或等价显式 schema，主要用于管理接口、配置和领域入口 | TS 类型不能验证网络输入；wire 校验仍由协议 schema 承担 |
| 存档 | 继续 SQLite；TS 访问首选 better-sqlite3 包装在仓储后 | 当前已经是 SQLite，先整理现有结构和迁移，不做无必要换库 |
| 测试 | 过渡期 pytest；TS 用 Vitest、fast-check；桌面/UI 用 Playwright 加真实客户端验收 | 测试夹具与语义断言跨语言共享，框架替换不重写预期结果 |
| 构建与发行 | 锁文件、Electron Forge、原生模块打包验证；按需要增加受控离线安装器 | 先修当前安装/便携制品完整性；发布版签名条件、证书与费用另行确认 |

Node 运行时版本以选定 Electron 实际内置版本为准；服务核心不依赖 Electron API，独立测试时使用匹配运行时。实施时选受支持的稳定版本并锁定精确依赖、包管理器及构建环境，不把某个写作时版本永久设为目标，也不把 `>=` 范围当锁文件。独立开发和命令行入口可用受支持的 Node LTS，但不得据此假设 Electron 中所有 API、SQLite 引擎和原生模块 ABI 相同。[T7]

### 2.3 为什么不直接选其他路线

| 路线 | 适用收益 | 主要代价或条件 | 本案取舍 |
|---|---|---|---|
| 长期保持模块化 Python + WinUI 3 | 变更最少，旧协议行为容易保持 | Python 与 C# 两套维护面，UI 与用户 Vue 能力不直接复用 | 明确保留的可行备选；TS 迁移收益不足时可在此停下 |
| Vue + Electron + TS 服务 | UI/领域主语言统一，本地桌面生态完整 | 安装体积、内存、Electron 更新和原生 SQLite 打包 | 长期主推荐，须经过迁移与资源开销验收 |
| Vue + Tauri + Rust 服务 | 可降低部分桌面承载开销 | 增加 Rust 工具链、WebView2/sidecar 分发与权限边界；业务未必必须用 Rust | 不作为默认；体积成为硬约束后再比较 [T11] |
| C#/.NET 统一服务与 WinUI 3 | 当前 Windows 外壳可复用，类型和系统集成成熟 | 业务仍需重写，Vue/TS 技能收益较低 | 若 Windows 集成成为主要工作量，可重新评估 |
| Java 或 PHP 本地后端 | 现有团队易承接部分业务 | 额外运行时、桌面打包和二进制协议适配 | 团队明确长期接手或已有服务资产时再选，不因熟悉就全面替换 |

不推荐首期引入微服务、消息队列、远程数据库、Redis 或容器编排。本地单用户服务用清楚的模块和一个事务所有者即可；需要多用户、远程访问或云部署时另立需求，不从这份方案扩大范围。

### 2.4 进程模型和跨语言迁移

长期默认由 Electron `utilityProcess` 托管 TS 服务，通过受约束的 MessagePort 协议交互；该机制提供 Node.js 子进程与 MessagePort，本方案据此选择它来隔离本地服务和 SQLite 访问。[T1] 主进程只提供命令白名单，不暴露任意 shell、文件路径写入或数据库执行入口。若使用 RunAsNode fuse 硬化，不依赖会被其影响的 `child_process.fork` 路线。[T2]

控制面默认走私有 IPC，不额外开放管理 HTTP。Fastify 承载已有 SDK/启动器的 HTTP(S) 契约；游戏 TCP 使用 `node:net` 与独立 framing。Zod 校验自有配置、IPC 命令和 DTO；不要把游戏恢复 schema 直接交给 Fastify 编译执行，其 schema 编译具有代码执行属性，只接收受信任的应用 schema。[T8]

Vue renderer 开启隔离和沙箱，关闭 Node 集成，经最小 preload API 调用；校验 IPC 发起方和入参，限制导航、新窗口与文件协议访问。浏览器内容永远不直接接触私钥或官方凭据。默认没有远程管理入口。若需要本机管理 HTTP，增加启动实例令牌、来源/Host 校验和 CSRF 防护；本机回环绑定不能单独当作身份认证。

Python 过渡服务由已授权启动动作创建，采用受控子进程和私有管道，明确拥有者、PID、实例 ID、退出和清理行为。不按进程名批量结束进程，也不因某端口被占用就杀掉占用者。未来独立无界面运行通过独立入口支持，不能让业务层依赖桌面 API。

TS codec 的替换门槛是：所有必需消息的黄金报文、字段存在性、命名空间、嵌套、未知字段策略和高位命令号测试通过；整数边界与旧实现差分一致；真实当前客户端大厅重登通过；已接通玩法回归不退化。不可表达的协议语义要显式扩展适配器或保留 Python 桥，不能为迁移而改 wire 行为。framing、头部和校验等要求逐字节一致的部分必须精确匹配；合法 protobuf 字段编码顺序可能不同，正文语义应按契约比较，不机械要求全部重编码字节相等。每次迁移只保留一个存档写入者，不让 Python 和 TS 双写正式存档。

64 位值端到端无损：Python 使用整数，TS 协议层使用 BigInt，JSON/控制接口用十进制字符串。SQLite INTEGER 为有符号 64 位，完整 uint64 ID 用规范十进制 TEXT；确需无符号数值排序时单独设计排序键或固定 8 字节大端 BLOB，不把 TEXT 字典序误当数值序。[T3] Protobuf.js 的能力以锁定版本和实际测试为准，不能沿用旧资料认定只能用某一种整数表示。需显式验证 BigInt 转换以及库默认丢弃未知字段的行为，要求保留的字段另设承载，不得在换库时无声丢失。[T4]

暂不默认采用 Node 内置 `node:sqlite`：本次查阅官方文档仍标为候选发布状态，而且 Electron 内置 Node 与独立 Node 版本不同。[T5] better-sqlite3 的同步调用放在服务工作进程，不能阻塞 UI；在仓储适配器显式配置并测试 `safeIntegers`，避免查询默认返回 Number 导致精度丢失；验证实际引擎版本、原生模块 ABI、安装/便携打包、并发和崩溃恢复。数据库访问保留 adapter，方便未来在有证据时切换驱动。首期使用参数化 SQL、仓储接口和带校验和的 SQL 迁移，不引入 ORM，便于审查种子、事务与 uint64 存储。

发行默认让 Vite 构建 Vue renderer，显式脚本构建主进程、preload 和服务包，Forge 负责 package/make；Forge 的 Vite 插件当前标为 experimental，不作为无条件稳定的一体化默认。[T9] better-sqlite3 作为外部原生依赖重建并从 ASAR 正确解包，安装版与便携版都做干净机器检查。Playwright 对 Electron 的支持仍属实验性，并涉及调试 fuse；仅用于 UI/壳自动化，不能用测试包代替加固发行包检查，也不能代替原生游戏大厅验收。[T10]

采用新栈前用同一真实用例比较旧/新实现的冷启动、空闲/操作内存、包大小、响应耗时和调试成本。先记录基线，再由承接者与用户确定可接受预算，不捏造性能目标。若维护收益不成立或分发质量不过关，停止迁移并保留已模块化的 Python 服务；完成 5.3.1 兼容的成果不应依赖是否最终换语言。

## 3 目标结构与迁移方式

### 3.1 模块边界

第一阶段仅新增最少模块与接缝，不要求拆进程。当前已有 `core.py`、`transport.py`、`login.py`、`account_db.py` 以及角色、装备、邮件、关卡等服务，优先复用其可验证逻辑，不另建一套无视现状的业务实现。[E8] 下图是稳定模块依赖方向，既适用于 Python 过渡期，也适用于之后的 TS 迁移：

```text
WinUI 3 或后续管理界面
  → 运行管理接口 → 预检、进程、版本状态、日志

游戏客户端
  → 本地 SDK / 网关 / 资源入口
  → 精确版本会话 → 分帧与版本化 codec
  → 协议适配器 → 领域命令或查询
  → 应用服务 → 事务和仓储 → 存档数据库
  ← 领域结果 ← 版本化响应映射 ← 编码及发送

只读内容快照 → 内容查询接口 → 应用服务
版本仓库 → 清单、schema、覆盖层、资源索引 → 各入口
```

领域层不接触 `cs_xxx`、`sc_xxx`、HTTP 路由、证书、资源文件路径；协议层不直接增减货币或写角色表。应用服务是事务边界。版本仓库只选取已登记制品，不拥有下载、迁移或信任证书的隐式权限。

### 3.2 建议目录

下列路径是目标模块位置，不代表仓库已经有这些文件。第一阶段可在 `v5_server/` 内增量建立，已有 `server_net.py`、`codec.py` 等通过薄包装调用新模块；新网络包使用不同名的 `network/`，避免与现有 `transport.py` 导入冲突；等测试覆盖稳定后再迁出旧逻辑。

```text
v5_server/
  bootstrap/                 路径解析、预检、依赖装配、生命周期
  compatibility/             清单、指纹选择、能力矩阵、准入规则
  network/                   SDK HTTP、网关分帧、连接及会话
  protocol/                  Schema IR、codec 接口、错误类型
  adapters/<tuple_id>/       SDK 契约、请求响应映射、覆盖层
  application/               登录、编队、战斗、领取等用例
  domain/                    账号、角色、库存、关卡、邮件模型
  persistence/               仓储、事务、幂等、迁移和备份
  observability/             关联 ID、事件日志、指标、脱敏
  legacy/                    逐步受控收纳旧实现，不新增业务依赖
  tools/                     静态导入、差异、校验、发行检查
artifacts/<tuple_id>/         不可变资源引用、schema、内容、清单
fixtures/<tuple_id>/          脱敏请求、预期语义、状态快照
migrations/                  有序、带校验和的存档迁移
release/                     支持矩阵、发布清单、恢复说明
```

模块通过构造参数或工厂装配；不要用导入副作用启动端口，也不要让代码从当前工作目录临时寻找资源。旧操作函数先挂到显式 `LegacyAdapter`，记录仍使用它的能力；每迁出一个用例便删除对应回落入口，禁止新功能继续绕过应用层。长期 TS 服务使用相同逻辑边界，例如 `services/local-server/src/` 下建立对应模块；先确定接口和夹具，再迁代码，不把目录搬迁当成功能重构。

### 3.3 关键接口契约

| 接口 | 输入 | 输出与约束 |
|---|---|---|
| `VersionResolver.resolve` | 指定客户端根、平台/渠道、实测指纹 | 精确 `ResolvedTuple` 或带差异的拒绝；不使用 mtime 决胜 |
| `SchemaRegistry.load` | 清单、schema、覆盖层哈希 | 完整且不可变注册表；引用不闭合则启动失败 |
| `Codec.decode / encode` | 版本会话、消息身份、载荷或值 | 有类型结果或明确错误；无“失败返回空字节” |
| `ProtocolAdapter.to_command` | 已验证 wire 消息、会话上下文 | 规范领域命令；保留版本和请求来源 |
| `ApplicationService.handle` | 领域命令、幂等键、事务上下文 | 领域结果、待发通知；无直接 socket 操作 |
| `ProtocolAdapter.from_result` | 领域结果、能力集 | 合约限定的响应序列，编码失败不发送伪成功 |
| `ContentRepository` | 固定内容快照和内容 ID | 只读记录或缺失错误；禁止跨快照自动查旧内容 |
| `UnitOfWork` | 用例和目标账号 | 原子提交或回滚；包含幂等记录与副作用账本 |

接口名是设计建议。可先用 Python `dataclass`、`Protocol` 或等价简单结构实现，避免为使用依赖注入而建设复杂框架。

```json
  "evidence": {"latest_checked_at": null, "source_url": null, "test_report_sha256": null}
}
```

JSON Schema 或等价验证器区分 `observed` 与可运行状态：候选记录允许未知值，正式清单要求所有与声明能力有关的必需值齐备。若目标不使用启动器，也须显式记录“不参与该入口”及依据，不能让空值兼作“不需要”。证书私钥、口令和用户绝对目录不进入可发布清单。

### 4.2 选择和绑定

1. 由显式配置解析真实客户端根与资源子目录，显示规范化路径；发现多个副本时列出差异并要求选择
2. 对原始索引及必要文件计算哈希，校验索引引用与清单；已有可信缓存须验证文件仍未变化
3. 按完整指纹查版本注册表；app/resource 和版本字符串只帮助缩小候选
4. 匹配成功后在会话建立前固定组合，连接存活期间不可热切 schema 或内容
5. 发现变化、未知版本或歧义时，普通启动拒绝，并说明缺哪个指纹；不写存档、不下发旧更新计划

首次适配 5.3.1 时，允许**已导入且精确锁定指纹的候选**进入隔离测试模式；此时运行的是登记候选，并非允许任意未知客户端。候选模式只指向克隆目录与测试存档，发布入口不可开启；测试结果不得自动晋级。

指纹变化后无需每次全盘重复哈希的优化可后做。无论是否使用缓存，发布前必须重新验证实际运行输入，不能只信缓存时间或目录名。

## 5 静态协议恢复与两层中间模型

### 5.1 恢复当前协议

当前 5.3.1 schema 从当前实际资源索引定位脚本包。旧 229 的恢复结果只作为提取器回归夹具，不是新 schema 的替代物。流程为：

`原始文件保全 → 哈希核对 → 格式识别 → 静态容器解析 → 静态 LuaJIT 声明恢复 → Schema IR → 引用和冲突检查 → 确定性 schema → 差异报告`

不执行游戏 Lua，不加载其运行时入口，不按陌生数据驱动任意文件写入。导入器限制文件大小、解压比、嵌套深度、条目数量和相对路径；越界或无法识别的字节码格式进入隔离状态。每个定义保留源包哈希、源条目、模块和定义定位信息，确保错误能回到输入。

旧流程曾发现 53 组短名冲突，涉及 124 个定义；新流程不得硬编码这一数量。所有定义以完整模块名加类型名标识；消息号必须与方向、版本组合一起查找。跨模块同名不合并，嵌套引用先解析完整身份。旧 p58 别名作为独立覆盖项审查，只有当前源证据仍支持时才应用。[E1][E3]

### 5.2 Schema IR

Schema IR 描述 wire 结构，最低包含：

- 类型身份、来源定位、方向和命令号映射
- 字段编号、名称、标量/wire 类型、重复性、存在性、默认值
- 嵌套类型完整身份、枚举范围及已知约束
- 未知字段处理策略和源证据

现有 `codec.py` 会原地修改全局 schema，并包含跨消息字段别名；`schema_default.py` 和 middleware 还有默认包回退。[E9] 应拆成“生成 schema、显式版本覆盖、领域映射”三份产物，运行注册表冻结后不再修改。

结构归一化后按稳定排序输出，并生成原始产物哈希与语义摘要。语义摘要有助于排除无意义排序差异，不能替代原文件哈希。重复执行同一提取输入应得到字节一致的 schema；生成器版本变化必须有差异报告。

解码后的规范消息对象可包含 `tuple_id`、`direction`、`message_key`、`presence`、`typed_fields`、`unknown_fields` 和 `source_ref`。64 位整数保持无损类型；若以后跨 JSON 边界，用契约约定的十进制字符串，不能经过 JavaScript 浮点数。字节字段、枚举、缺字段与显式默认值必须可区分。

### 5.3 领域模型

领域模型表达稳定业务语义，例如 `AccountId`、`CharacterId`、`Formation`、`BattleSession`、`InventoryDelta`、`MailClaim`，不复刻某版 protobuf 字段。

适配器承担 wire 到领域的显式转换，例如某一版本用数组传编队，另一版本用位置映射，最终都生成经校验的 `SaveFormation`。无法证明等价的字段保留为待查，不随意丢弃、补零或解释为成功。领域模型变更、Schema IR 变更和存档迁移分别版本化。

### 5.4 失败语义

至少区分 `UNKNOWN_TUPLE`、`SCHEMA_MISSING`、`UNKNOWN_MESSAGE`、`UNRESOLVED_TYPE`、`INVALID_FIELD`、`UNSUPPORTED_CAPABILITY`、`INTERNAL_ERROR`。合法零字段消息是成功值；找不到定义是错误，两者不能共用 `b""`。[E3]

已知版本允许的可选未知字段可按该契约保留或忽略；未知消息不能套通用成功。响应格式已知时返回该版本能理解的错误；格式未知时保留诊断并受控断连，不编造错误包。解码、命令校验或响应准备失败时，不提交业务写入。提交后网络发送失败应允许安全重试，而不是尝试“撤回”已经提交的事务。

## 6 第一目标的最小大厅纵向链路

### 6.1 先建立请求地图

对当前指纹组合记录以下阶段和真实请求顺序，不把旧版消息号当成新版契约：启动入口、SDK 初始化与版本查询、本地身份建立、网关握手、账号信息、基础内容同步、大厅初始化、退出重登。

旧 `cs_10038 → sc_10039` 是有用的调查线索，仍须在当前资源定义和样本中确认。[E2] 每一阶段记录入口、必要字段、响应顺序、下一阶段触发条件和超时。样本来自用户自己的明确授权操作；没有运行样本时，静态结果只能标“推定契约”，不得验收为大厅通过。

现有登录初始化从 SQLite `login_push` 按顺序加载，并存在生成器、JSON、旧 blob 的回退。[E10] 首轮必须同时核验这份种子与顺序，而非只修代码和 schema。抽出版本化 `LoginPlan`，逐帧注明来源、必要性、动态字段及顺序；生成失败应报错，不偷偷换成旧 blob。历史 `seq <= 192` 是当前代码行为，不能直接成为当前 5.3.1 推送清单。

### 6.2 最小适配范围

仅实现实际进入大厅所需的 SDK 和网关契约、最小本地账号状态及大厅必需角色/内容数据。初始化字段必须来自当前 schema、内容配置及观察到的语义。可以建立明确的测试账号种子，但不能用无限资源、全角色或空成功包掩盖未知必需字段。

将大厅所需请求挂到显式能力集合 `hall_minimum`。其他请求单独登记为未实现，并返回契约允许的失败或禁用相应测试入口。若一个请求直接触发未实现玩法，不能为了大厅截图伪造其成功状态。

SDK 路由按目标版本注册契约；现有末尾 HTTP 200 加空 `data` 的兜底必须移除或限制为有真实契约的端点。[E4] 启动器全功能不是前置条件：若已验证的直接启动路径可完成本地登录，先完成该入口；启动器更新、公告等另列能力，避免强迫客户端下载旧资源。

### 6.3 大厅通过标准 G1

- 当前目标的来源、核实时间及完整运行组合有记录
- 用目标客户端克隆目录和独立测试存档实际进入大厅，退出后可重登
- 登录前后 EXE、索引、脚本等受保护文件哈希一致，没有客户端降级或资源回落
- 关键请求、响应和状态均能关联；不存在被吞掉的编码异常或假成功兜底
- 重启本地服务端后仍可重复上述流程，必要账号数据保持一致
- 证据明确写“本地大厅通过”，同时列出未验收的角色操作、战斗、邮件等能力

完整领域拆分、数据库大迁移和玩法接通都在 G1 之后。若大厅确实必须写少量账号状态，先在独立测试存档中用最小事务边界完成，不为此提前重构所有历史存档。

## 7 领域功能与存档事务

### 7.1 数据模型和存储选择

现有存档层已使用 SQLite，建议继续使用并先整理其边界，单一服务拥有数据库写权限；WinUI、Vue 或协议桥都通过应用服务访问。内容配置与用户存档分开：内容是不可变版本快照，存档是可迁移的玩家状态，种子只用于显式创建新档。

建议最少实体：账号与本地会话、角色及养成状态、编队与槽位、库存与余额账本、关卡进度、战斗会话、邮件与附件、领取记录、请求幂等记录、待发送事件、迁移记录。名称是逻辑模型，不要求第一阶段全部建表。

现有 `init_schema` 集中了自动迁移、自愈和种子写入；固定树中未见所依赖的完整发行数据库及独立 `db_schema.sql`，因此先核实实际包和存档，再设计显式迁移。[E11] 不直接把当前初始化函数包装成“无副作用预检”。

主外键、唯一约束与版本号用于守住不变量；金额和数量用有界整数，并验证范围。每条进度与奖励关联内容快照，遇到内容 ID 复用不得默认为同一物品。删除或不可用内容保留映射或墓碑记录，不能产生悬空引用。

### 7.2 并发与事务

初期按账号串行处理写用例；数据库再通过唯一约束和事务兜底。读取可并发，写队列设长度上限和等待超时；连接数、包大小、每连接未完成请求数也必须有界。不要把全局大锁包住网络收发或整个战斗过程。

采用 SQLite 时，验证 WAL、忙等待、崩溃恢复与所选同步级别；备份使用数据库支持的一致性备份方式，不能直接复制正在写入的主文件而遗漏日志。检查实际绑定的 SQLite 引擎包含官方已披露 WAL-reset 问题的修复，不能只看 Python/Node 包版本。[T6]以后若确实需要多用户并发，再以仓储契约评估其他数据库。

一个写用例的顺序为：解码和输入校验 → 读取幂等结果 → 开事务并检查版本 → 校验资格 → 计算状态变化和响应所需数据 → 验证可编码性 → 写状态、账本、幂等记录及待发事件 → 提交 → 发送。外部 I/O 不放在长事务中。并发冲突可有限重试，但不得重新生成不同奖励。现有 `Core._run_operation` 的事务主要包住 `apply`，响应编码及补帧在其后，因此“编码失败仍无写入”是待实现门槛，并非当前已有保证。[E12]

### 7.3 角色和编队

服务端验证角色存在、归属、可用状态、位置约束及内容版本；客户端提交不作为拥有该角色或资源的证明。保存编队和其版本号同事务提交；重复请求返回同一结果；重连读取与提交后状态一致。历史“无法完成角色选择并进入战斗”拆成可定位步骤，不以一个“战斗失败”统称。

### 7.4 战斗和结算

服务端创建 `battle_id`，绑定账号、关卡、编队版本、内容版本和必要随机种子。推荐状态机为：`CREATED → STARTED → FINISHED → SETTLED`，另有 `ABORTED / EXPIRED`。每次转移检查前态及资格，明确体力何时扣除、失败是否退还、重连如何恢复，不能先从其他版本猜规则。

客户端上报战斗结果只是输入。服务端至少验证战斗身份、关卡资格、状态顺序、合理范围和奖励配置；奖励数量由服务端计算，不能直接接受客户端传来的货币增量。若无法重现战斗模拟，只声明已验证的本地流程与边界校验，不宣称具有完整反作弊或战斗权威模拟能力。

结算、奖励账本和进度更新在同一事务中，`battle_id + settlement_kind` 建唯一约束。断线重试返回已提交的原结算，不再次发奖。中途退出、失败、超时、客户端崩溃和重启分别测试。

### 7.5 邮件和幂等

邮件打开、列表、内容读取、附件领取是独立用例。领取时校验归属、有效期、可领取状态和附件内容；“已领取标记、库存变化、账本、幂等结果”原子提交。批量领取的全成功/部分成功语义由目标版本契约决定。

幂等键优先使用协议内稳定请求标识；若没有，则设计并持久化领域操作 ID，例如战斗会话或邮件附件领取键。不能只用短时间窗口内的载荷哈希代替业务身份，否则相同的合法连续操作可能被错误去重。过期策略必须保留足够业务唯一性，客户端换连接也不能绕过领取约束。

### 7.6 迁移和恢复

迁移脚本带序号、输入格式、输出格式及校验和；记录运行版本与结果。先在存档副本演练并执行不变量检查，成功后才能提出对正式存档迁移。新增种子数据绝不覆盖已有档。

现有档无法打开、校验失败或迁移中断时，进入只读诊断/隔离，保全数据库及关联 WAL/SHM，不将其当成“缺新档”自动初始化空档、删档或自愈覆盖。先停止写入并按一致性恢复流程保全文件，在副本执行适用的 `integrity_check`、`foreign_key_check` 和业务不变量检查；确认可恢复状态后，按用户同意的恢复点切换。

正式切换前明确来源、目标、覆盖范围及不可逆影响，并取得相应同意。默认恢复方式是版本对应快照，而非未经证明可逆的 down migration。回到旧快照会丢失后续进度时，必须单独说明取舍。备份保存在受控私有位置，公开发行包只带空档或无个人信息的测试种子。

## 8 资源 SDK 与运行管理

### 8.1 不可变资源

官方客户端原目录默认只读。导入、试验及迁移都使用独立克隆目录；版本登记不授予更新原目录的权限。资源仓库按内容哈希存储或校验，索引指向同一组合中的文件，禁止“缺新文件就找旧目录”。

导入先写临时区，检查容量、大小、哈希、索引闭合及路径安全；全部通过后完成落盘并切换小型版本指针。资源包自身不原地覆盖。Windows 文件占用或文件系统无法原子替换时，以状态日志和可恢复步骤实现切换，保留旧入口；切换前停止相关会话。不能把部分准备成功的目录标为 ready。

SDK 下发的资源计划必须精确对应当前已批准组合；未知版本返回不支持，不发送 229 或其他默认更新计划。默认禁止自动降级。正常运行不隐式连外网下载，首次缺资源应明确列出缺项，由获授权的导入步骤补齐。[E5]

### 8.2 TLS 和端口归属

分别管理 TLS 证书身份、信任状态、监听者、HTTP 就绪和业务就绪。一个明确的进程拥有每个监听端口；第一阶段优先沿用可测试的单入口，是否以后增加反向代理由实际需要决定，不预设必须引入代理栈。

默认只绑定 `127.0.0.1`；需要 IPv6 时单独验证 `::1`，不自动使用 `0.0.0.0`。端口冲突显示 PID 和配置来源。默认不创建 `netsh portproxy`，也不默默修改 hosts、系统代理、防火墙或证书信任。当前主程序自检分支之前会执行端口清理，桌面外壳启动也会清理端口占用者；必须先改成真正只读的 preflight，不能直接把现有 `--self-check` 当安全探针运行。[E13]确需改动时先列出具体项并获取授权，再记录还原操作。

每个安装实例生成独立本地密钥，私钥限制访问，不使用仓库携带的共享私钥作为可信生产密钥。服务证书的 SAN、有效期、签发链与实际访问名称逐项验证；信任根安装以满足客户端的最小范围为限，属于独立确认步骤。卸载或切换时只清理本工具创建且身份匹配的项目，绝不按模糊名称删除用户已有证书。

### 8.3 管理外壳

管理界面显示实际运行目录、tuple、能力状态、端口拥有者、schema 哈希和启动失败原因。进程管理调用结构化控制接口，不解析随意变化的日志文本来推断“已就绪”。

启动生命周期采用 `CREATED → PREFLIGHT → READY → DRAINING → STOPPED`，失败进入 `FAILED`。预检完成前不开放游戏业务入口；可单独开放仅本机可用的诊断接口。就绪应区分传输、依赖、存档和声明能力，不把“进程存在”或“443 有监听”显示成“可以玩”。

## 9 可观测性和错误定位

统一日志写入管线，Python 过渡层使用结构化事件，TS 服务建议 Pino，将 stdout、stderr 和应用事件归一收集，使用结构化 JSONL、轮转和明确的编码策略；避免两个独立写入者覆盖同一文件。[E6]

每次启动生成 `run_id`，每连接与请求生成关联 ID。事件至少包含时间、阶段、tuple、schema 哈希、消息号/端点、领域用例、耗时、结果、错误类别及堆栈。版本或运行路径在启动事件中完整记录，普通请求引用其 ID，避免重复刷屏。

默认不记录令牌、口令、官方账号凭据和完整原始包。需要协议样本时使用独立的显式采样开关与脱敏导出，限制大小和保留时间；测试仓库只留脱敏夹具。导出诊断包前扫描秘密与个人信息。

最低诊断面包括 schema 缺失/冲突数、未知请求数、解码失败、编码失败、写队列深度、事务冲突和幂等重放。一次大厅失败应能区分：TLS 未连通、SDK 未实现、组合不匹配、schema 不全、数据不合法、响应顺序错误或客户端资源缺失。

## 10 可以交给实施者的工作包

### 10.1 第一轮只做三个小型验证

**SP01 保全并识别当前 5.3.1。** 输入是用户当前可正常启动的客户端及可取得的旧备份。只读取原目录，建立完整清单和测试副本，核实 EXE、SDK、索引、脚本与来源；输出 `client-inventory.json`、当前候选清单和差异/未知项。检查命令本身必须只读，不调用含端口清理或数据库自愈的现有启动流程。检查复制后哈希一致，原目录未改变。完成标准是得到可信当前输入，不要求此时连接本地服务端。

**SP02 从当前脚本恢复 schema。** 依赖 SP01。输入是当前脚本原始字节与旧提取回归夹具；输出带来源定位的 Schema IR、版本化 schema、命名冲突和语义差异报告。测试确定性、引用闭合、格式拒绝和字段边界。完成标准是当前协议结构有可追溯证据；不因消息数与旧版接近而通过。

**SP03 确认大厅最小契约。** 依赖 SP01，可与 SP02 并行做静态部分；动态部分使用匹配 schema。输入是当前入口和经授权取得的请求轨迹；输出 `hall-contract.md`、端点/消息顺序、必需数据和未知语义列表。完成标准是能明确每一步应返回什么、仍缺哪些证据；若样本不足，报告具体缺口，不能编造映射。

三个验证结束后做短评审：当前目标是否完整、提取器是否足够、登录阻断属于哪个层、完成大厅需改哪些最小区域。只有这里获得的证据才能决定第一批具体补丁，不预先承诺大量重写。

## 11 测试设计与发布门槛

### 11.1 测试层次

1. **静态与制品测试**：schema 完整、覆盖层有来源、资源引用闭合、登录种子与顺序齐全、依赖锁齐全、包内文件哈希正确
2. **协议单测和属性测试**：正常/边界整数、重复字段、嵌套、缺字段、拆包/粘包、截断、非法长度、压缩比上限、解压错误、未知消息；验证规范值往返，不对合法未知字段盲目要求逐字节相等
3. **适配器契约测试**：wire 夹具转领域命令、领域结果转目标响应序列；动态 ID、时间和随机数按明确规则归一化
4. **领域与数据库测试**：不变量、事务回滚、唯一约束、并发冲突、幂等；在提交前、提交后发送前等故障点注入中断
5. **真实客户端端到端测试**：在用户有权使用的机器、隔离测试副本及测试档执行；记录运行组合、初始状态、操作与结果
6. **恢复和离线测试**：干净发行、原子切换、存档恢复、断外网冷启动；范围只覆盖实际声明能力

整数测试明确覆盖 2^53−1、2^53+1、2^63−1、2^63、2^64−1、负 int64、缺省与显式零；协议测试包括 packed/unpacked、同名嵌套类型与未知枚举。每个 tuple 使用独立 schema 注册表，避免新版本修改全局类型而污染旧连接。

当前源码存在内嵌自检，但固定树未见独立测试目录和 CI 配置；新增测试不能写成“原来完全没有测试”。当前 `requirements.txt` 的宽版本范围也不能替代发行锁文件。[E14]

纯静态分析、测试设计和夹具准备不需要操作用户设备。真实客户端运行验证须作为后续独立实施动作取得授权，不能因本技术计划而自动开始。

### 11.2 关键反例

- 输入未知资源编号、改名索引或两个同显示版本副本：拒绝歧义，不选择“最后修改”的文件
- 移走 schema 或删除一个嵌套定义：启动预检失败，不等到登录后悄悄断线
- 旧 `sc_45109`、`sc_45111` 引用在当前源中找不到：对应能力隔离，不猜字段补齐 [E7]
- 模拟编码失败：事务不提交；提交后断线再试：返回已提交结果，不重复扣费或发奖
- 更新中断、磁盘不足、文件被占用：候选不可用，旧目录和指针可恢复
- 直接请求另一账号角色或邮件：拒绝归属错误，不能只靠 UI 隐藏
- 程序从不同工作目录启动：清单、schema 和数据根一致

### 11.3 门槛分级

| 门槛 | 允许声明 | 禁止扩大的结论 |
|---|---|---|
| G0 输入保全 | 当前候选已锁定，可重复静态分析 | 当前客户端已兼容 |

| G3 可发布组合 | 声明范围的包、存档与恢复测试通过 | 自动兼容未来官方版本 |

307/229 的历史用户确认保留为旧记录；是否能重现、是否有完整快照必须单列。它不能替代当前目标 G1，也不能因旧备份暂时缺失而去改坏已经恢复的 5.3.1。

## 12 官方更新到最终封存

### 12.1 每次更新的流水线

`发现 → 保存来源和原字节 → 隔离导入 → 指纹登记 → 结构差异 → 语义审查 → 候选适配 → 大厅回归 → 已支持功能回归 → 人工准入 → 受控发布`

当前按人工触发设计，不假定存在稳定官方更新 API，也不启动定时监控。来源应是官方公告、用户实际更新或用户有权取得的安装材料；保留平台、渠道、时间和授权范围。

静态差异至少包括消息/字段/类型/存在性/默认值/枚举、嵌套引用、SDK 端点、请求顺序、内容 ID 与奖励规则。结果分为“可加性候选”“明确破坏”“语义待查”；新增字段不自动等于兼容，静态相同也不证明业务语义没变。

每个覆盖项携带目标 tuple、源依据、变更原因、测试夹具和撤销条件。禁止把旧补丁复制进新版本后直接标通过。与已有能力无关的新增玩法可明确不支持；影响大厅或既有玩法的未知语义会阻断相应能力晋级。

### 12.2 支持矩阵与发布记录

每行对应精确 tuple，列出：候选状态、来源/时间、最新目标或旧回归身份、大厅/角色/编队/战斗/邮件各自结果、测试证据哈希、已知缺陷、存档格式和恢复目标。状态包括已观察、已导入、静态通过、大厅通过、指定流程通过、隔离。

发布记录引用不可变清单与证据。新版本失败时，继续保留旧已验证组合，但明确其版本和能力，不能自动降级当前客户端或把旧包伪装成最新版。客户端、schema、覆盖层、内容和存档迁移必须作为一个受控组合评审。

### 12.3 官服结束前后的安排

持续伴随官方更新的目标以官方服务实际状态为准，不把某个计划日期视为已宣布停服，也不保证未知未来协议必然可适配。维护过程中就逐步归档可合法保全的依赖，避免把下载留到 CDN 消失之后。

最终记录“最后观察到的官方版本”和“最后通过离线验收的组合”，允许两者不同。封存包包含源代码提交、构建说明、锁定运行时与依赖、原始材料来源及哈希、schema 与覆盖层、内容、测试夹具、支持矩阵和恢复步骤。个人存档、密钥与公开制品分开保存。源码按仓库 NCR-1.0 许可保留声明并审查使用范围；该许可不自动授予官方客户端资源再分发权。[E15]

逐项列出外部依赖：官方认证、CDN、公告、第三方 SDK、时间或其他服务。可合法本地替代的部分实现独立契约；无法替代的能力标为限制。不能以绕过账号认证、证书安全警告或未授权获取资源来完成所谓离线验收。
