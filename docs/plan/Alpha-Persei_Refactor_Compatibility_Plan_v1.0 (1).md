## 1 结论与目标

近期目标调整为：**先让实施时核实的最新官方客户端，使用与它匹配的资源和协议进入主界面，再接通各项功能。** 本文将主界面与主大厅视为同一验收目标。不得通过回落旧资源或降级客户端达到这一门槛；完整架构改造也不应成为推进最新客户端登录的额外前置工程。

阶段 0 先保存已经进入主大厅的旧组合。当前唯一有用户运行确认的组合是 **app 307 / resource 229，对应当前索引 v5.2.1，补入恢复的协议 JSON 后进入主大厅**。它只作为回归与恢复基线，不能计为新第一阶段完成。这项结果也不能外推为 resource 321 / v5.3.1 兼容或战斗、邮件、全部玩法可用。

已知 resource 321 / v5.3.1 是待核验候选，不代表写作时或未来实施时的官方最新版。实施第一步须按目标平台和渠道核实当时最新版本及来源，再锁定 EXE、SDK、资源索引、schema 和服务端组合。本版仅更新需求优先级，不进行当前版本查询或代码实施。

重构的长期目标是：在官服继续更新期间，持续接收和评估用户有权取得的官方客户端更新，维护经过验证的伴随服务端兼容版本，直至官服完全停服；停服后仍能保存和恢复最后经过验证的离线运行组合。每次更新都须留下版本、差异、测试与回退证据，不能靠隐藏降级维持表面可用。

这是维护范围与验收目标，不是对未知未来协议的兼容保证。本版不设未经确认的停服日期、监控频率、完成工期或维护负责人，也不据此启动自动监控。现阶段按人工触发的更新接入流程设计。

## 2 本次故障复盘

### 2.1 版本发生了变化

最初上传的资源索引是 app 307 / resource 321，标记 v5.3.1。HTTPS 恢复后，DD 观察到客户端实际执行资源更新；随后检查的实际资源索引变为 app 307 / resource 229，标记 v5.2.1。

固定提交使用非递归 `os.listdir` 扫描，并按文件修改时间选择索引；桌面端自动查找确认 `StreamingAssets\Windows` 存在后，却返回游戏根目录，再将该路径传入扫描参数。扫描根目录与索引所在目录存在错配；未知 resource 321 也会进入默认 229 的回落路径。[S9] 结合前后索引变化，**发生了至少部分资源回退或重对齐**是强推断。当前缺少 EXE 前后版本、哈希及完整文件差异，尚不能断言整个客户端完整降级。后续文档、测试和补丁名称必须保留这一边界。

### 2.2 传输故障先于协议故障

本机原先安装的 CA 指纹为 `97B36880C405741E03B4936EEB70DE57D7574C22`，实际服务使用的新 CA 指纹为 `9DC7C584E5A6EC27457EE043D86427D13FD6D070`。DD 手动导入匹配证书后，又移除了错误的 `127.0.0.1:443 → 127.0.0.1:13443` 转发；当时 13443 无监听，而 Python 监听 `0.0.0.0:443`，随后 HTTPS 通路恢复。

这说明证书、监听地址、转发配置和应用协议必须分层诊断。单独看到 HTTPS 可连接，不能证明 SDK、启动器或网关握手已经正确。

### 2.3 网关卡住与缺失 schema

启动器调用的 `get_update_version`、`get_index_config` 等接口未获得完整预期语义；固定提交的 SDK 路由末尾会把未匹配请求返回为 HTTP 200 和空 `data`，可能掩盖未实现接口。[S2] 直接启动游戏后，Admin/SDK 登录可继续，但网关阶段卡住。

抓包中可识别出 156 字节的有效 `cs_10038`，服务端 ACK 后 FIN，未见 `sc_10039`。固定提交在登录成功日志之前调用 `codec_encode("sc_10039", ...)`；外围又静默捕获 `OSError` 等异常。[S1] 独立运行 `decode_schema.py 0800 sc_10039` 明确报 `FileNotFoundError`，指出缺少 `lua_proto_messages.json`。[S3]

DD 确认安装版实际目录为 `E:\Program Files\AetherGazer_Server\v5_server`，另行检查便携包也缺少该 JSON。独立命令的异常是依赖缺失的直接证据，**不是实际网关调用栈**；网关路径、抓包现象和补回文件后的运行结果共同支持其为本次登录阻断的关键原因。

### 2.4 恢复过程与验证边界

从当前 229 索引定位到 `scripts64`，对应资源路径为：

`game\AetherGazer_Data\StreamingAssets\Windows\8\6\86add1e9d150efa2464ec96f0579a0b9.ys`

上传文件按 18 MiB 分片后重组，大小和哈希核对通过；文件有 10 字节 NUL 前缀，随后为 UnityFS v8，Unity 版本为 `2022.3.62f3c1`。此次仅静态读取文件格式和声明，没有执行游戏 Lua。共提取 10,267 个 LuaJIT TextAsset，其中 92 个协议文件包含 3,061 个消息定义、6,889 个字段。

53 组跨模块短名称冲突涉及 124 个定义。恢复 JSON 使用带模块命名空间的索引名，并同步修正嵌套引用；另保留一个有源定义依据的 p58 兼容别名，满足 Alpha 现有补丁引用。最终为 3,062 个消息条目、6,892 个字段，1,368 个嵌套引用全部解析。3,061 个源定义与固定公开数据提交逐字段、逐引用一致，并经两次独立静态复核。[S5]

2026-10-11 02:10（UTC+8），DD 确认安装该 JSON 后成功进入主大厅。之后尝试过邮件，但结果未明确；仍无法完成角色选择并进入战斗，具体卡点待补证。因此状态为“主大厅通过；战斗受阻；邮件结果及其他玩法尚未验证”，后续业务修复暂缓，不能宣称游戏已完整修复。

## 5 重构边界与接口要求

### 5.1 保留可工作实现并逐层替换

把旧基线登录链路纳入可重复测试，优先完成最新客户端所需的版本化编解码和最小登录适配；进入主界面后，再随功能接通逐步抽取领域与数据模块。不要同时更换语言、数据库、网络栈和业务实现；新语言或框架是否必要，应由测试结果、维护成本与实际瓶颈决定。

建议形成以下边界，不要求立即拆成独立进程：

- **运行管理层**：路径、依赖、证书与端口检查、进程生命周期、健康状态
- **版本与资源层**：组合清单、资源索引、离线资源、支持矩阵、迁移和回滚计划
- **SDK 与启动器适配层**：分别管理对应接口；最小启动路径单独验证，不把启动器全量实现作为登录层的隐含依赖
- **版本化协议层**：分帧、schema、命名空间、编解码、版本覆盖层、错误分类
- **领域服务层**：账号、角色、编队、关卡、奖励、邮件等稳定模型，通过适配器转换不同版本字段
- **持久化层**：事务、幂等、存档版本、迁移与备份恢复

领域模型不直接散布 `sc_xxx`、资源路径或旧版本字段。每个适配器声明输入组合、输出契约及能力范围；不能只按某个消息号猜测版本。跨版本共用逻辑必须有语义一致证据。

### 5.2 协议处理必须可追溯

schema 生成结果与人工兼容覆盖层分离。每项覆盖必须注明来源、适用组合、原因、测试与撤销条件。命名空间是消息身份的一部分，不能自动把同名但不同结构的类型合并。现有 p58 别名应作为有依据的覆盖记录，不能推广成任意短名兜底规则。

缺失消息定义、引用未解析、必填字段缺失或非法字段值时，停止该请求的编码与业务提交。不得用空字节、默认成功包或硬编码“成功”掩盖错误。[S3] 合法零字段消息与“查无定义”必须有不同结果类型。新增可选字段是否容忍，应按该版本契约验证；不能把所有未知字段一概当错误，也不能将所有新增字段一概当兼容。

保留输入来源与字段到源定义的映射，提供确定性生成和往返测试。测试范围除 wire type 外，还包括必填性、枚举、数值范围、嵌套目标、字段语义和响应顺序。

### 5.3 观测与错误接口

日志至少包括时间、运行实例、连接/请求关联 ID、版本组合、阶段、命令或端点、schema 哈希、耗时、错误类别及异常堆栈。默认不记录凭据、会话令牌和完整原始载荷；必要采样先脱敏。启动失败应指明缺哪个文件、当前在哪个目录、需要哪个版本，不能仅提示“网络错误”。

未知 HTTP 端点采用注册契约允许的状态和错误体；不假定所有客户端都接受同一种 HTTP 状态码。诊断接口和服务就绪接口分开：进程活着不等于依赖齐全，更不等于业务就绪。

## 6 官方更新接入流程

所有新版本先进入隔离目录，任何阶段失败都保留当前可用版本。官方客户端目录默认只读，不静默改资源、不拼接跨版本文件、不自动降级。需要受控迁移时，必须先获得对明确源版本、目标版本及改动范围的同意。

### 6.1 发现与获取

由官方发布信息、用户实际更新或已获授权的元数据触发接入。当前未确认稳定的官方更新 API，不能凭空设计轮询地址或宣称已设监控。记录发现时间、来源、平台、地区/渠道和版本标识；从用户有权访问的官方客户端、安装包与元数据中取得材料，归档原始字节及 SHA-256。

官方账号侧的流量样本仅来自用户自己的、明确授权的正常操作。不得使用他人账号、绕过认证、共享账号秘密，或为了重放测试反复付款、消耗稀缺资源、删除角色。原始样本私有保存，进入测试仓库前去标识化。

### 6.2 静态导入与差异分级

在离线或隔离环境解析资源和协议，不执行不受信任的 Lua。生成以下差异：

- 文件新增、删除、改名、哈希变化，索引引用是否缺失
- 消息与字段增删，编号/类型/必填性/重复性/嵌套引用变化
- 相同字段但语义、枚举或默认值改变
- 角色、道具、关卡等内容 ID 的增删与复用，配置关联完整性
- SDK、启动器、资源分发契约和初始化顺序变化
- 存档数据格式与业务规则变化

把差异分为“候选可加性变化”“明确不兼容变化”“语义待查”。新增字段不自动等于安全：若新角色要求新业务状态或新关卡改变结算规则，仍需业务适配。静态一致也只能说明已比较范围一致。

### 6.3 适配与验证

首次实施按阶段 1 先适配大厅必需链路；以下完整业务验证随阶段 2 展开。后续官方更新则先重验新客户端大厅，再重验此前已经接通的功能，不能因沿用旧功能代码就直接标记通过。

先生成版本化 codec 和必要覆盖层，再接入领域适配器与内容版本。使用脱敏历史样本检查旧行为，使用新版本正常操作样本确认新语义。对奖励仅发一次、货币不异常减少、角色与编队引用有效、关卡资格一致等业务不变量进行独立断言。

只在克隆客户端、独立服务端目录和测试存档中跑端到端验证。每个失败必须能关联到具体版本差异、请求和数据状态；不能为了“进游戏”持续补通用成功包。

### 6.4 准入与发布

支持矩阵同时记录版本状态与逐功能结果：

| 状态 | 含义 | 允许范围 |
|---|---|---|
| 已观察 | 只知道版本存在 | 展示信息，禁止运行与迁移 |
| 已导入 | 原文件齐备且哈希可信 | 隔离分析 |
| 静态通过 | schema、资源和引用检查通过 | 测试环境运行，未宣称可玩 |
| 登录通过 | 指定组合已进入主大厅 | 明示仅登录范围，不自动开放未测功能 |
| 流程通过 | 列明的端到端用例通过 | 仅在所列能力范围发布 |
| 隔离 | 有不兼容、未知来源或失败 | 拒绝普通运行，保留只读诊断 |

当前 307/229 应标“登录通过，无法完成角色选择并进入战斗，邮件待确认”；321 应标“已观察，当前兼容未验证”。“流程通过”必须附用例名单，不能代替“全功能兼容”的证据。矩阵还需记录最后验证日期、测试制品、已知缺陷、维护状态和回退目标。

矩阵还要区分“旧回归基线”和“本轮最新目标”。只有本轮经官方来源核实的最新目标达到“登录通过”，才完成第一阶段；旧组合的同名状态不能替代它。若实施中出现更晚官方版本，先记录为独立候选，不混用其文件；需重新核对目标及验收范围，不把已过时的目标继续称为最新版。

### 6.5 受控迁移与回退

迁移前给出文件和数据差异、下载来源、哈希、空间需求、会覆盖什么、哪些变化不可逆及如何恢复。获得明确同意后，先做一致性备份并验证可读；在新目录完成准备和测试，成功后原子切换版本指针。原子性不足的环境要有可恢复的阶段日志，崩溃时保留旧入口。

客户端、schema、服务端、内容及数据库按组合切换。数据库回滚应使用对应快照；只有经过验证可逆的迁移才允许执行降级脚本。若恢复旧快照会丢失升级后进度，必须提前说明并再次确认具体取舍。升级中断、磁盘不足、校验失败均不得留下半新半旧的可运行目录。

## 7 测试与发布门槛

### 7.1 分层测试

| 层级 | 必测范围 | 通过依据 |
|---|---|---|
| 制品与启动 | 干净安装、便携包、任意工作目录、缺依赖、坏哈希、端口与证书错误 | 所有失败可诊断；未就绪时不开放业务 |
| 协议 | schema 冲突、坏引用、边界值、必填字段、截断/重复/未知包、往返编码 | 无静默成功；输出符合指定版本契约 |
| 第一阶段最新客户端登录 | 最新版本身份、匹配资源、SDK、网关、大厅初始化、退出重登 | 不回落旧资源，实际进入主界面且可重现；版本、日志和截图/运行记录一致 |
| 第二阶段角色功能 | 正常创建/选择角色、角色状态读取与保存 | 服务端与客户端状态一致，存档可恢复 |
| 角色与编队 | 列表、养成信息读取、保存编队、非法或删除 ID | 无悬空引用，重连后保持一致 |
| 战斗 | 进入、资源加载、开始、退出/失败、完成、结果回传 | 每阶段都有可核实状态；不以加载成功代替结算成功 |
| 奖励与邮件 | 发放、领取、重复领取、重复结算、超时重试、重连 | 事务幂等；余额、库存和邮件状态只发生预期变化 |
| 持久化 | 进程中断、事务失败、并发请求、备份恢复 | 不出现部分提交、重复奖励或损坏存档 |
| 版本迁移 | 升级、失败中断、回退、旧存档恢复 | 原基线可重现；数据损失范围明确且已获同意 |
| 离线保存 | 禁止外网后的冷启动与核心流程 | 不依赖临时 URL、官方 CDN 或官服在线认证服务 |

离线保存的最后一项是架构目标，需在合法取得的本地材料与授权范围内设计，不能通过绕过官方账号系统实现。若某功能无法脱离外部服务，应列为明确限制，而不是报告离线通过。

第一阶段只执行进入主界面所需的制品、协议、传输和登录测试，并验证没有自动降级。若大厅初始化必需最小账号或角色数据，只实现有契约依据的必要部分；角色养成、编队、战斗、奖励和邮件等完整功能待第一阶段通过后再接通。该门槛不因其他玩法尚未实现而被改写为失败，也不能宣称这些玩法已通过。

### 7.2 用例记录要求

每个用例记录前置版本组合、初始存档快照、操作、预期消息和数据变化、实际结果、脱敏日志、制品哈希及失败原因。样本禁止保存可用令牌和他人隐私。真实时间、随机数、动态 ID 等非确定性字段应按规则归一化，不能简单要求所有响应字节一致。

最新客户端主大厅验收后，第二阶段应测试角色选择到战斗加载的边界；本次卡点优先成为回归用例。邮件要分开记录“打开”“显示”“领取”“持久化”结果，目前不能给其中任一项补写成功。

## 8 分阶段交付与待办

| 阶段 | 交付物 | 进入下一阶段的门槛 |
|---|---|---|
| 0 保存旧基线 | 307/229 组合清单、备份与恢复说明、现状支持矩阵 | 旧主大厅可重现；备份经验证；旧目录与新目标隔离 |
| 1 最新客户端进入主界面 | 最新版本核实记录、匹配客户端/资源/schema、最小 SDK 与网关适配、启动预检和必要日志 | 经核实最新组合实际进入主界面并能重登；无资源回落、无客户端降级；证据可重现 |
| 2 接通功能并逐步重构 | 按优先级接通角色、编队、战斗、结算、奖励、邮件；同步完善领域与数据边界及发行工具 | 每项功能在第一阶段验证组合上通过完整流程、幂等与持久化测试；大厅回归保持 |
| 3 持续跟进官方更新 | 逐版本导入、差异报告、兼容适配、支持矩阵、迁移与回退记录 | 每个新目标先过最新客户端大厅门槛，再验证已支持功能；失败隔离且保留旧验证组合 |
| 4 停服后最终封存 | 离线依赖归档、已知限制与最终恢复演练 | 符合第 9 节封存条件 |

阶段 1 内可并行核实版本、静态提取和必要适配，但角色、战斗等完整功能接通必须等待阶段 1 门槛通过。阶段 3 的准入规则从首次导入就适用，不必先建设自动化平台。负责人、复核人及发布批准人均待确定；发布者不能用未复核的静态生成结果替代运行验证。不预设一周完成或指定全新技术栈。

待办顺序：确认旧基线备份 → 实施时核实最新官方客户端 → 锁定匹配 EXE/SDK/资源/schema → 完成最小登录与大厅初始化 → 取得无降级的主界面运行证据 → 按确认优先级接通功能。resource 321 / v5.3.1 仅是已知待核验候选，307/229 仅是回归基线。Miku 等单项业务修复不抢在最新客户端主界面目标之前。

## 9 直至停服及停服后的保存要求

官服仍更新时，每次候选按第 6 节接入。资源、协议或核心语义发生不兼容时，应明确报告阻断范围和所缺证据，保留上一验证组合；“持续兼容”不能解释为无条件接纳所有未来更新。

只有可核实的官方消息和实际服务状态才可确认停服阶段，不能猜日期。停服前在用户授权和可取得范围内保存所需客户端、资源索引及依赖；不能等 CDN 下线后再假定仍能下载。保留至少一个最后已验证组合，另行标记最后观察到的官方版本；若两者不同，禁止把后者改名为“最终已验证版”。

最终封存包包括：

- 原始材料与哈希清单、必要本地资源，及其来源和可使用范围
- 服务端源代码提交、构建说明、锁定运行时与依赖、schema 与版本覆盖层
- 内容和种子数据、存档格式、迁移历史、私有备份恢复说明
- 支持矩阵、已知限制、脱敏测试夹具和回归结果
- 无外网条件下从干净环境恢复到已验收核心流程的记录

外部服务依赖须逐项列出并验证替代或限制。最终存档的完整性检查、恢复方式及维护交接应可离线执行。任何无法合法保全或尚未验证的能力都要明确标注；不将未经授权的官方资源或私人存档公开分发。

## 10 未决事实与最终验收清单

### 仍需补证

1. 实施时目标平台/渠道的最新官方版本及来源；旧基线与新目标各自的 EXE、SDK、启动器、资源和运行时版本及哈希

4. 实际网关异常堆栈；已有独立 schema 报错不能替代它

6. 基线备份是否完成，以及恢复是否经过验证
7. 待支持的平台、渠道和玩法范围，维护与验收责任人
8. 现有 codec 人工覆盖与源协议的差异；源码引用但当前协议中不存在的消息应如何处理

第 8 项已有具体例子：静态复核发现可选玩法代码引用 `sc_45109`、`sc_45111`，当前上传客户端对应请求定义也缺失；不能把它们编造成“提取遗漏”或补猜字段，应隔离相应能力并查明版本来源。[S7]
