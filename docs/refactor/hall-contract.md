## 当前可用的历史线索

两份原计划都强调旧 app307 / resource229 的大厅记录仅属历史回归证据，不能代替当前目标。兼容计划要求按版本分别记录身份和能力；技术计划 G1 要求真实目标客户端、匹配资源及退出重登。

旧日志里的 cs_10038 → sc_10039 可以作为搜索样本的提示。它们不能单独确定 SDK 到网关的转换、响应含义、会话字段、后续推送顺序或成功态。schema 只描述消息结构；没有当前流量或服务端有效契约时，不据此补造字段语义。

当前 SDK HTTPS 请求和响应正文未知。PktMon 网卡采样可留下 TCP 记录，但如果内容由 TLS 加密，不能从 pcapng 假定可读出 HTTP 正文。原始网络记录可能包含凭据，应留在本机并先脱敏；不要把令牌或原始完整载荷放进仓库或聊天。

已有抓包的接口统计块记录：接口 0 接收 37,073 包、接口丢弃 16 包；接口 1 接收 24,178 包、接口丢弃 51 包；接口 2 接收 381 包、接口丢弃 0 包。操作系统丢包等计数未记录，保留未知。接口丢包不能直接定位到游戏会话；目标流观测前缀的序号、重传和重叠检查已通过。游戏 F255 有 13 字节相同重传，重组时仅计一次。本机只读元数据报告为 `desktop/qa/business/official-startup-metadata-v3.json`；时间计算使用整数 tick 与有理数，避免浮点舍入改动纳秒时间。

去重后共 238 个帧事件（网关上/下各 1，游戏上 17、下 219）。游戏下行 compress=0 有 210 条，compress=1 有 9 条，后者全部通过有输出限额的 zlib 解压。全部 238 帧已用当前 schema 递归核对字段编号、线类型、引用消息、packed 重复字段、UTF-8 字符串和 required 存在性，均通过。两条未压缩消息（68151、83016）开头碰巧满足 zlib 签名条件，解压却失败；以帧压缩标志选择原始 body 后 wire 结构合法，不能凭 body 前两个字节替代压缩标志。脱敏事件元数据为 `desktop/qa/capture-evidence/official-startup-events.json`，不含 body、字段值、IP 或 HTTP 头值。每个方向使用流内帧序号；跨方向时间只表示采样观察顺序，不代表因果关系。

匹配器不使用默认值补缺，也不判断数值取值域。单帧最大观测字段数为 23,980；实际限制为 1 MiB、100,000 字段和嵌套深度 32，细节列表有长度上限。早期 10,000 字段限额导致三条大消息误报 incomplete，统一限额后复跑通过。required 检查按 protobuf 的 singular message 合并规则处理，repeated message 各自独立；实际轨迹没有重复 singular message 合并。匹配器 15 项边界测试由主代理复跑通过。格式依据可参照 [Protocol Buffers 编码文档](https://protobuf.dev/programming-guides/encoding/)。

纯 Python 实现位于 `v5_server/network/framing.py`，提供显式方向的单帧编码/解码与增量 decoder；body 保持线上原始字节，不执行 protobuf 解码或压缩签名猜测。客户端整帧上限 1 MiB，服务端整帧硬上限 65,537 字节；每次 feed 上限 1 MiB、最多返回 4,096 帧，调用方须分块。非法头或超限进入持续失败状态，EOF 有残帧明确失败，正常 EOF 后不再接收数据。该模块不监听端口，也不建立账号、会话或业务成功态。

该生产模块的 15 项测试通过；主代理用去重后的真实 238 帧分别按碎片和粘包输入，全部解码、重编码逐字节一致，四个方向都没有残帧。最终代码 SHA-256 为 `bdd8eabbc9b0c395f9f227b9fd19a48c038ae2c697e48d3cdc3343db2725d3dd`，本机证据为 `desktop/qa/business/tcp-framing-roundtrip-final.json`。这项离线验证不等于本地游戏运行。

## LoginPlan 边界

当前已有同版本轴的帧顺序材料，但没有可执行的新版 LoginPlan。旧 schema、旧服务器日志、SQLite 中历史 login_push 行为或旧序号边界，都不能单独生成当前目标的推送列表和顺序。观测到的 219 个下行帧中可能包括账号内容、活动同步、分批传输与后续请求响应，不能全部标成必需初始化。每条计划项需注明同版本证据、必要性、静态字段结构、动态值来源、顺序依据和失败语义。未知项保持未决，不用旧 JSON、旧 blob 或空成功响应静默回落。

[login-observation-307-321.json](login-observation-307-321.json) 保存 238 条方向内序列、180 条对应消息的核心字段目录和源定位，绑定 PCAP / schema / 脱敏事件 SHA，不包含载荷或字段值。它明确 `runtime_login_plan=false`，把必要性、动态值提供者、测试种子和失败行为标为 unknown，供后续用例实现逐项补证；不能作为重放或自动推送配置直接运行。

已有官方正常登录样本可用于继续对照当前静态 schema、服务端请求处理及大厅状态变化，无需因文件较大重采样。后续需要补充操作边界或其他流程时可参照 [hall-capture.md](hall-capture.md)；SDK HTTPS 正文仍须另有证据。

## G1 验收清单

以下项目全部有同一目标组合的可复核记录后，才能写 G1 通过：

- 记录版本来源、核实时间、EXE / SDK / 资源 / schema / bundle 指纹和实际运行目录。
- 在客户端克隆与独立测试存档上运行；原始客户端目录不用于试写。
- 当前客户端实际进入大厅，退出后重新登录可重现；服务端重启后再验证一次。
- 登录前后核对受保护客户端文件哈希，无资源回退或客户端降级。
- 请求、响应、服务端状态和错误可按版本及阶段关联；没有被吞掉的编码异常或假成功兜底。
- 记录未验收的角色操作、编队、战斗、结算与邮件能力；大厅通过不自动代表这些能力通过。

本清单是验收条件，不是通过记录。当前没有任何当前版本大厅运行项可标为完成。
